# 평가셋 v2 설계 (실사용 질의 + 풀링 판정)

- 작성일: 2026-11-02
- 상태: 구현됨(도구) — 평가셋 생성 전
- 관련: `scripts/verify/eval_retrieval_gate.py`, `artifacts/citec-kb-retrieval-fix-20261028/` (기존 evalset·README), `docs/CITEC_KB_REMAINING_WORK_BACKLOG_20261029.md`

## 1. 배경과 목표

동의어 후보 마이닝 시험(2026-11-02)에서 후보 18개를 반영해도 게이트 지표가 전혀 변하지 않았다. 효과가 없어서가 아니라, **평가셋이 그 변화를 볼 수 없었기** 때문이다. 현재 평가셋의 약점은 다음과 같다.

- `evalset-2026-10-28.json`(50 cases): 정답 문서에서 질의를 파생해 쉬운 편(자기참조 편향). 파일의 `caveats`에도 명시돼 있다.
- 동결 홀드아웃(30건): 장애 질의 중심이고 규모가 작다. 일부는 `ground_truth_confirmed: false`다.
- 군마다 통과 수와 hit@3만 있어 개선·악화가 우연인지 판단할 수 없다.

목표:

- 검색 개선의 전·후 차이를 통계적으로 판단할 수 있는 평가셋을 만든다 (60~80 질의).
- 기존 `eval_retrieval_gate.py`가 그대로 읽는 형식으로 만든다.
- 실사용 분포를 반영하고 자기참조 편향을 줄인다.

## 2. 결정 사항

| 항목 | 결정 |
|---|---|
| 질의 출처 | 운영 실사용 질의 + 합성 혼합 |
| 정답 판정 | 풀링 + LLM 보조 판정, 사람은 O/X만 |
| LLM 실행 위치 | 개발 서버(OpenRouter). 개발 코퍼스는 운영과 거의 같음(확인됨) |
| 운영 쓰기 | 어시스턴트는 하지 않는다. 로그 추출 SQL은 사용자가 실행 |

## 3. 질의 출처

### 3.1 실사용 질의 (30~40건)

- 운영 `mcp_access_log`(`path='/v1/search'`, `query_summary` 의 `q=` 값)에서 읽기 전용 SQL로 추출한다. 추출은 사용자가 실행한다.
- 코드가 제외하는 것: 기존 평가셋·홀드아웃 질문 문구와 같은 질의(하네스·측정 호출), 완전 중복, 5자 미만, 식별자 형태만 있는 질의.
- 사용자가 추출 TSV를 직접 훑어 고객명 등 민감한 줄을 지운 뒤 개발 서버로 옮긴다.
- `query_summary`는 512자로 잘려 있다. 잘린 질의는 제외한다.

### 3.2 합성 질의 (30~40건)

실사용에 없는 슬라이스를 채운다.

- `vocab`: 한·영, 약어 표기 차이
- `pointer`: 매뉴얼·문서 탐색형 (pointer-only 문서가 정답일 수 있는 질의)
- `symptom`: 현업이 쓸 법한 증상 서술

자기참조 편향 완화:

- 생성 프롬프트에 "정답 문서의 단어를 그대로 쓰지 말 것"을 지시한다.
- 코드로 질의 토큰과 정답 문서 제목 토큰의 겹침률을 계산해 상한(기본 0.5)을 넘는 질의는 버린다.

## 4. 정답 판정

1. **풀링**: 질의마다 여러 설정(multi_query on/off 등)의 상위 10개를 합쳐 후보 풀을 만든다. 질의당 약 10~15개.
2. **LLM 보조 판정**: 개발 서버 LLM이 후보별 관련도 0/1/2와 근거 문장을 제안한다. 근거 문장이 후보 문서 본문에 실제로 있는지 코드가 검증하고, 없으면 그 판정은 무시(미판정)한다.
3. **사람 검수**: 질의당 후보 5~8개에 O/△/X를 표시한다. O = 직접 답함(`expect`), △ = 부분 관련(`also_ok`), X = 무관(제외). 표시하지 않은 후보는 비관련으로 간주하고(풀링 한계, 보고서 `unlabeled_candidates`에 집계), O가 없는 질의(△뿐 포함)는 제외한다. 시트는 기본으로 LLM 힌트를 숨겨 사람이 먼저 판단하게 한다. 질의당 1~2분, 전체 1~2시간.
4. **검수 시트**: 서버 없이 쓰는 정적 HTML 한 장. O/△/X를 누르고 JSON으로 내려받는다. API 변경과 DB 쓰기가 없다.

## 5. 형식

기존 `cases` 스키마와 같다: `id`, `group`, `kind: "search"`, `q`, `filters`, `expect`, `k`.

- 사람이 O로 표시한 문서만 `expect`에 넣는다. △(부분 관련)는 `also_ok`에 따로 저장한다 (게이트는 무시). LLM 관련도 0/1/2는 후보 제안일 뿐 라벨이 아니다.
- 군 이름: `v2_real`, `v2_vocab`, `v2_pointer`, `v2_symptom`.
- 각 케이스에 `source`(real/synthetic), `reviewed_on`, 분할(`split`: dev/frozen)을 기록한다.

## 6. 게이트 확장

- 평가셋 군별로 recall@10과 MRR을 집계한다 (기존 통과 수·hit@3 유지).
- `compare`가 전·후 차이의 **페어 부트스트랩 95% 구간**을 출력한다. 구간이 0을 포함하면 "차이 불분명"으로 표시한다.
- `v2_` 접두사 군은 **통계적으로 판정**한다: recall@10 차이의 95% 구간이 전부 음수일 때만 실패한다(케이스 단위 pass→fail은 참고 출력). 공통 케이스가 8건 미만인 군은 판정하지 않는다. MRR은 참고용이다.
- v2 군의 케이스 id 집합이 before/after에서 다르면(한쪽에만 있는 군 포함) 게이트가 **실패**한다. 전/후는 같은 평가셋으로 측정해야 한다.
- 기존 홀드아웃·evalset 군의 동작과 종료 코드 규칙(1 = 머지 금지)은 바꾸지 않는다.

## 7. 분할과 동결

- 절반은 개발·튜닝용(`dev`), 절반은 동결 홀드아웃(`frozen`). 분할 키는 합성 질의의 seed 문서 id(없으면 질의 문구)라서 같은 문서에서 나온 질의가 양쪽에 걸치지 않는다.
- 동결 후에는 `frozen`을 보고 튜닝하지 않는다. 동결 시각을 파일에 기록한다.

## 8. 비범위

- 코드에 정답 ID나 질의별 규칙을 넣지 않는다. 라벨은 `artifacts/` 아래 데이터 파일로만 둔다.
- 운영 DB 쓰기, 운영 코퍼스를 외부 LLM에 보내는 일은 하지 않는다.
- 평가셋 자동 갱신, 온라인 A/B 테스트.

## 9. 한계 (문서·README에 명시)

- 풀링은 현재 시스템이 올린 문서 위주로 후보를 만들기 때문에 **절대 recall은 부풀려질 수 있다.** 전·후 상대 비교는 유효하다.
- 합성 질의는 겹침률 필터로 편향을 완화할 뿐 완전히 제거하지 못한다.
- 실사용 질의 수는 운영 로그(2026-10-14 이후 약 3주)에 달려 있고 테스트 호출이 섞여 있어, 기대보다 적을 수 있다. 그 경우 합성 비중을 늘린다.
- LLM 판정은 후보 제안일 뿐이다. 최종 판정은 사람이다.

## 10. 테스트 (네트워크 없음)

- 겹침률 필터, 근거 구간 검증, 질의 위생·중복 제외 필터
- 라벨 import 검증 (잘못된 ID, 중복, 형식)
- 부트스트랩 함수 (고정 시드로 알려진 입력의 구간)
- 생성된 평가셋이 `eval_retrieval_gate.py run`의 입력으로 로드되는지 (소규모 가짜 서버 또는 로더 단위 테스트)

## 12. 미결 사항
