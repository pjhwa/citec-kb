# 동의어 후보 마이닝 설계 (Fabrix 오프라인 배치)

- 작성일: 2026-11-02
- 상태: 구현됨 (리뷰 반영 갱신 2026-11-02)
- 관련: `docs/CITEC_KB_REMAINING_WORK_BACKLOG_20261029.md`, `apps/api/app/retrieval/search_synonyms.py`

## 1. 배경과 목표

운영 로그(2026-10-08~11-02) 기준 `/v1/chat`(LLM 답변 생성)은 11건, `/v1/search`는 5,392건이다. 서버 LLM의 가치는 요청 경로의 답변 생성이 아니라 **오프라인 배치 보강**에 있다고 판단했다.

첫 대상은 검색 동의어 후보 마이닝이다. 현재 `SYNONYM_GROUPS`는 손으로 관리해 확장이 안 되고, 남은 검색 실패(`sym-2502`, `sym-2508`, inode 등)는 대부분 어휘 간극이다.

목표:

- Fabrix가 티켓 제목과 증상 슬롯에서 동의어 후보를 **제안**한다.
- 코드가 말뭉치로 **검증**하고, 사람이 **승인**한 것만 검색에 반영한다.
- 반영은 검색 전용이다. `lexicon_version`을 바꾸지 않아 그래프 재빌드와 배포가 필요 없다.

## 2. 결정 사항

| 항목 | 결정 |
|---|---|
| 승인 후 반영 경로 | DB 테이블 + 승인 API (배포 없이 갱신) |
| LLM 입력 | support_history 티켓 제목 + 증상 슬롯 (질의 로그는 운영에 없음) |
| LLM 산출물의 지위 | 후보일 뿐 근거가 아니다. 코드 검증과 사람 승인을 통과해야 반영 |
| 운영 쓰기 | 어시스턴트는 하지 않는다. 마이너 실행과 approve는 사용자가 수행 |

## 3. 데이터

alembic 마이그레이션 1개. 테이블 `search_synonym_candidate`:

- `id`
- `terms` (jsonb, 용어 목록)
- `terms_key` (정규화된 용어 집합, unique 제약으로 중복 후보 방지)
- `status`: `proposed` / `approved` / `rejected` / `disabled`
- `evidence` (jsonb): 용어별 DF, 검증된 근거 티켓 ID, LLM 근거 문구
- `run_id`, `model`
- `decided_by`, `decided_at`, `note`
- `created_at`

## 4. 마이너 (배치 스크립트)

기본 dry-run, 실행은 사용자.

1. **DF 범위는 입력 선별이 아니라 검증 단계의 필터로 적용한다.** LLM이 한·영 교차 표현을 찾으려면 티켓 원문 맥락이 필요해서 용어를 미리 잘라 줄 수 없다. 티켓(제목+증상 슬롯)은 그대로 LLM에 보내고, 반환된 용어의 DF가 범위 밖이면 코드가 걸러낸다.
2. **Fabrix 호출**: 약 100건씩 배치로 보내 JSON 그룹 후보와 근거 티켓 ID를 받는다. `llm_fabrix.py` 어댑터를 재사용한다.
3. **코드 검증 필터** (LLM 출력을 신뢰하지 않는다):
   - 한글 1~2자 용어 불허 (과거 오탐 이력: 행→hang). ASCII 용어도 3자 미만은 거부
   - 각 용어의 코퍼스 FTS DF가 최소치(`--df-min`, 기본 3) 이상, 상한(`--df-max`, 기본 1500) 이하 (과도하게 흔한 용어는 지연 회귀 위험). DF는 2000에서 잘라 세므로 `--df-max`는 2000 미만이어야 하고, DF 필터 뒤 용어가 2개 미만으로 줄면 근거를 다시 검증한다
   - 그룹 크기 최대 6
   - 기존 `SYNONYM_GROUPS`와 중복되는 후보 제외
   - LLM이 인용한 근거 티켓 본문에 용어가 실제로 존재하는지 문자열로 확인. 티켓당 최소 `--min-terms-per-ticket`개(기본 2, 동의어 쌍이 한 티켓에 같이 안 나오면 1로 완화)가 있어야 검증된 티켓이고, 검증된 티켓이 2건 미만이면 폐기
   - 한글 포함 용어는 조사가 붙어도 인정되도록 대소문자 무시 부분 문자열로 비교한다 ("OOM이", "메모리 부족으로"). 순수 ASCII 용어는 더 긴 영숫자 열에 박혀 있으면 불인정
4. 통과한 후보를 `proposed`로 저장한다 (`--commit` 또는 별도 `import`).
5. 중단 후 재개: 기본 `run_id`는 `--out` 경로에서 파생되므로 같은 `--out`으로 다시 실행하면 이어서 진행한다. 완료된 배치만 `<out>.progress.jsonl`에 체크포인트하며 키는 배치의 티켓 ID 해시(`ids_hash`)다 (티켓이 바뀌면 재처리). LLM/처리 오류 배치는 체크포인트하지 않아 재실행 때 다시 시도된다.
6. 출력: stdout은 JSON 1개(`run_id`, `stats`, `commit`). 종료코드 3은 부분 실행(`llm_error`/`proc_error`/`parse_fail` > 0)이며, 이때 `--commit`은 `--allow-partial` 없이는 건너뛴다.

처리 범위 기본값은 최근 2년 티켓이다. 전체 티켓 수를 확인한 뒤 조정한다.

## 5. 승인 API

`/v1/lexicon/synonym-candidates`:

- 목록 조회 (상태 필터, 근거 포함)
- 일괄 가져오기 (import, 개발 DB 검증용)
- `approve` / `reject` / `disable`
- 쓰기(import/approve/reject/disable)는 senior/admin 역할. 결정 엔드포인트는 빈 본문 허용. import는 항목 2000개, terms 20개(각 100자), evidence 8192자 JSON 한도. `AUTH_MODE=off`에서는 이 게이트가 무의미하므로 운영 `.env` 확인이 필요하다 (런북 참고).

런타임 병합:

- `search_synonyms()`가 코드 그룹과 DB의 `approved` 그룹을 합쳐 사용한다.
- 캐시 60~600초.
- DB 오류 시 코드 그룹만 사용한다. 검색은 이 기능 때문에 실패하지 않는다.
- 단어 경계 매칭, 양방향 그룹, 다단어는 구문 매칭 등 기존 동작을 유지한다.
- 동의어 변형은 title ILIKE 스캔에서 제외한다 (8ce9bf8의 지연 회귀 수정 유지).

## 6. 게이트 검증 흐름

1. 운영에서 마이너를 실행한다 (Fabrix는 운영에서만 접근 가능). 결과 JSON을 내려받는다.
2. 개발 DB에 import하고, 개발 전용 플래그 `SEARCH_SYNONYMS_INCLUDE_PROPOSED=1`을 켠 상태에서 `scripts/verify/eval_retrieval_gate.py`를 실행한다.
   - holdout recall@10 후퇴 없음이 통과 조건이다.
   - p50/p95 지연도 함께 기록한다 (게이트 자체는 지연을 판정하지 않으므로 별도 측정).
3. 게이트를 통과한 후보만 운영 API에서 approve한다. 승인은 사용자가 한다.

## 7. 비범위

- 하드코딩된 정답 ID, 질의별 규칙
- 그래프와 임베딩 변경, DB lexicon(`lexicon_version`) 변경
- 자동 승인
- 요청 경로에서의 LLM 호출

## 8. 테스트

- 검증 필터 단위 테스트: 한글 1~2자, 근거 부족, DF 상한, 중복, 그룹 크기
- API 상태 전이와 권한 테스트
- `search_synonyms()` 병합, 캐시, DB 장애 시 코드 그룹 폴백 테스트
- Fabrix 호출은 가짜 응답으로 대체 (재시도와 부분 실패 포함)

## 9. 위험과 대응

| 위험 | 대응 |
|---|---|
| LLM 환각으로 잘못된 동의어 | 근거 티켓 문자열 검증 + 사람 승인 |
| 흔한 용어로 인한 오탐과 지연 | DF 상한, ILIKE 제외, 게이트 지연 측정 |
| Fabrix 쿼터·지연 | 배치 크기 조절, 재개 가능, 실패 배치만 건너뜀 |
| 개발과 운영 데이터 차이 | 개발 검증은 참고용이며, 승인 후 운영 지연을 같은 명령으로 재측정 |
| 승인된 그룹이 검색을 깨뜨림 | `disable` API로 즉시 비활성화, DB 오류 시 코드 그룹으로 폴백 |

## 10. 미결 사항

- 처리 범위(최근 2년)는 전체 티켓 수 확인 후 확정한다.
- DF 하한·상한의 구체 값은 구현 계획에서 코퍼스 분포를 보고 정한다.
