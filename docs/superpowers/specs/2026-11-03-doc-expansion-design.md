# 문서 확장(검색용 설명문) 설계 — pointer-only 요약 파일럿

- 작성일: 2026-11-03
- 상태: 초안 (사용자 검토 대기)
- 관련: `docs/superpowers/specs/2026-11-02-evalset-v2-design.md`, `artifacts/citec-eval-v2/`, `apps/api/app/synonyms/` (검증 방식 재사용)

## 1. 배경과 목표

평가셋 v2 기준선(2026-11-03)에서 `v2_pointer` recall@10 = 0.125 (1/8), `v2_vocab` = 0.37이다. 실패한 정답 문서를 확인하니 "pointer-only"라는 이름과 달리 본문이 있다(dev `confluence_map` 78,272건, 본문 길이 중앙값 1,598자). 원인은 내용 부족이 아니라 **제목·앞부분이 질의 어휘와 맞지 않는 것**이다.

| 질의 | 정답 문서 제목 |
|---|---|
| 데이터센터 바닥 발 빠져서 넘어진 사고 | 1월 3주차 팀 월요미팅 |
| 콘솔 위젯 목록 불러오는 api | GET /console/api/support/widgets |

목표: LLM이 문서마다 **검색용 설명문**(한 문단 + 키워드)을 미리 만들어 검색 색인에 더한다. 요청 경로의 LLM 호출은 없다. 효과는 v2 평가셋 전/후 비교로 판단한다.

## 2. 결정 사항

| 항목 | 결정 |
|---|---|
| 대상 선정 | 코드 규칙(제목 정보량이 낮은 `confluence_map`). 평가셋 정답을 보고 고르지 않는다 |
| LLM | 개발 서버 OpenRouter (`z-ai/glm-5.2`), 오프라인 배치, 재개 가능 |
| 저장 | 별도 테이블 `doc_expansion` (원문·`documents` 불변) |
| 반영 | 검색 색인에 합침. 플래그로 끌 수 있음 (`SEARCH_DOC_EXPANSION`) |
| 운영 | 어시스턴트는 운영 쓰기·LLM 호출을 하지 않는다. 운영 적용은 개발 측정 후 별도 결정 |

## 3. 대상 선정 규칙 (코드, 질의·정답과 무관)

`source_type = confluence_map` 이면서 본문 200자 이상이고, 제목이 다음 중 하나:

- 회의·주차·미팅·회의록·월간·주간 등 정기 모임 표기
- HTTP 메서드로 시작하거나 `/`로 시작하는 API 경로
- 날짜로 시작하는 제목 (`2023-12`, `12월`, 6~8자리 숫자)

dev 기준 약 12.9천 건이다 (회의 7.5천, API 1.4천, 날짜형 7.9천, 중복 포함). 규칙은 `selection.py`에 정규식으로 두고 단위 테스트한다. 확장 가능하도록 규칙 이름을 결과에 기록한다.

## 4. 생성

- 입력: 제목 + 본문 앞 4,000자(자르는 기준은 설정값). 본문은 `<doc>` 펜스로 감싸 지시문 주입을 막는다(evalv2 judge 방식).
- 출력(JSON): `summary`(≤300자, 한국어), `keywords`(5~10개, 현업이 쓸 법한 표현·한영 병기 포함).
- 검증(코드, LLM 출력을 신뢰하지 않음):
  - JSON 스키마, 길이 상한
  - 키워드는 본문(전체) 근거 여부를 `term_present`로 확인해 두 집합으로 기록한다: `keywords`(검증을 통과한 전체)와 `grounded`(그중 본문에 근거가 확인된 부분집합). 한글은 부분 문자열, ASCII는 경계 일치. 근거 없는 키워드를 버리지 않는다: 본문에 이미 있는 단어는 청크 FTS가 어차피 찾으므로, 어휘 간극을 메우는 것은 본문에 없는 현업 표현이기 때문이다.
  - 폐기 규칙: 검증을 통과한 `keywords`가 3개 미만이면(또는 summary가 비면) 문서 전체를 버린다. `keywords`가 3개 이상이면 `grounded`가 비어 있어도 보관한다(`grounded` 모드에서는 색인할 키워드가 없을 뿐이다).
  - 1~2자 한글 키워드 금지(`is_valid_term` 재사용)
  - `summary`의 근거 검증은 하지 않는다(요약은 의역이므로). 대신 검색에는 키워드를 우선 쓰고 summary는 보조로 둔다(§5).
- 빈 응답(Fabrix 필터형)·429 등은 `empty_response` 계수와 재시도, 체크포인트로 재개한다 (synonym `mine_batch` 패턴).
- 1단계는 200건 샘플 생성 후 사람 눈으로 품질을 본다(무작위, 고정 seed). 통과 시 전체 대상 실행.

## 5. 검색 반영

- 문서별 `doc_expansion(document_id, summary, keywords, grounded, tsv_all, tsv_grounded, rule, model, run_id, created_at)` 1행.
- 모드: `SEARCH_DOC_EXPANSION=off|grounded|all` (기본 `off`). `grounded`는 본문 근거가 확인된 키워드만 색인(안전, 효과 제한적일 수 있음), `all`은 summary + 모든 키워드를 색인(효과 크고 오탐 위험). 어느 모드를 운영에 쓸지는 평가 결과로 정한다.
- 색인: 기존 FTS 경로에 확장 텍스트를 별도 가중치 컬럼/tsvector로 합친다. 정확한 방식(생성 컬럼 vs 별도 tsvector 조인)은 구현 계획에서 현재 `search.py`의 FTS 쿼리 구조를 읽고 정한다.
- 반환 본문·근거(`evidence_grade`, 인용)는 원문 그대로다. 확장 텍스트는 **랭킹 신호일 뿐 근거가 아니다.** 응답에 확장문을 노출하지 않는다.
- `SEARCH_DOC_EXPANSION=off`(또는 미설정)이면 기존 동작과 동일(회귀 방지).
- 임베딩(벡터) 경로는 이번 범위에서 바꾸지 않는다.

## 6. 평가와 통과 기준

- 평가셋: `artifacts/citec-eval-v2/evalset-v2-all.json` (46건), 같은 파일로 전/후 측정.
- 성공: `v2_pointer` 또는 `v2_vocab` recall@10 개선(부트스트랩 구간은 참고). `v2_real` 악화 없음, 기존 홀드아웃 게이트 통과, p95 지연 악화 없음(별도 측정).
- 실패/무효과도 결과로 기록한다. 대상 규칙이 정답 문서를 포함하는지는 사후에 보고만 하고 규칙을 평가셋에 맞춰 바꾸지 않는다.

## 7. 비범위

- 정답 ID·질의별 규칙, 요청 경로 LLM 호출, 임베딩 재생성, 운영 쓰기, 자동 갱신 스케줄
- 확장문의 사용자 노출

## 8. 위험과 대응

| 위험 | 대응 |
|---|---|
| 환각 키워드로 오탐 | 본문 근거 검증으로 `grounded` 부분집합 기록, `grounded`/`all` 모드별 측정 |
| 확장 텍스트가 랭킹을 왜곡 | 별도 가중치, 플래그로 즉시 끔, `v2_real` 회귀 확인 |
| 생성 시간·비용 | 200건 파일럿 후 전체, 체크포인트 재개, 동시성 제한 |
| 개발·운영 차이 | 개발 측정은 참고이며 운영 읽기 전용 측정으로 확정 |

## 9. 테스트 (네트워크 없음)

- 대상 선정 규칙(양성·음성 제목 예시)
- 출력 파싱과 키워드 근거 검증(한글 조사, ASCII 경계, 1~2자 금지, grounded 분리, 3개 미만 폐기)
- 체크포인트 재개, 빈 응답 재시도 계수
- 검색 반영: 플래그 off 동일성, on 시 확장 키워드로 문서가 매치됨(스크래치 DB)
