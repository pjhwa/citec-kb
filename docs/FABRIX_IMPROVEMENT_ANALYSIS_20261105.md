## 0. 요약 (결론 먼저)

1. **지금까지 Fabrix를 "검색 신호를 보강하는 데" 쓴 시도는 5건 모두 recall@10을 올리지 못했다** (동의어 마이닝, 문서 확장 렉시컬 AND/OR, 문서 확장 벡터, 청크 복구 후 재측정). 실패한 방식이 서로 달라 보여도 공통점이 있다. 모두 **"어느 단계가 병목인지 모른 채" 인덱스 쪽 신호를 더한 것**이다.
2. **제1원칙으로 보면 다음 개선의 출발점은 Fabrix 기능이 아니라 측정이다.** 평가셋이 작아(46건, pointer는 8건: 케이스 1개가 recall 0.125) 효과가 있어도 보이지 않고, 정답 문서가 어느 단계에서 탈락하는지(후보 풀 진입 / 순위 / 청크 부재)를 분해한 기록이 정식 도구로 없다.
3. **LLM의 본질적 비대칭**: 의미를 이해하지만 느리고(호출당 수 초~수십 초) 비결정적이며 쿼터가 있다. 검색 경로는 빠르지만 어휘만 안다. 따라서 **LLM은 오프라인에서 의미 지식을 한 번 계산해 빠른 구조(사전·라벨·색인·초안)로 굳히는 데** 쓰고, 요청 경로에는 조건부 폴백으로만 넣는다.
4. **권장 순서**: (P0) 병목 분해 도구화 + 평가 감도 확보 → (P1) 비용이 거의 없는 **상한 실험**(질의 재작성·재순위를 오프라인으로 먼저 돌려 "되는 아이디어인지" 확인) → (P2) 결과에 따라 한 갈래만 구현. 지식 생산(실패 버킷 초안, IssueFrame LLM 추출)은 검색 recall과 **독립된 축**이라 병행 가능하다.
5. **하지 말 것**: 문서측 렉시컬 확장의 추가 변형, 상시 요청 경로 LLM 호출, 평가셋에 맞춘 규칙. 근거는 §6.

## 2. 제1원칙 분해

### 2.1 KB의 존재 이유
사용자의 질문에 **정확한 근거 문서**를 연결하고, 근거가 없으면 없다고 말하는 것. 구성 요소는 셋이다.

1. **코퍼스 안에 답이 있는가** (지식의 존재·구조)
2. **질문이 그 답에 닿는가** (검색: 후보 진입 → 순위)
3. **닿은 답을 믿고 쓸 수 있는가** (근거 등급, 인용 검증, 생성 품질)

Fabrix로 개선할 수 있는 곳은 이 세 곳 어디든이다. 검색 recall(2)만 본 것이 지금까지의 편향이다.

### 2.2 정보 흐름과 손실 지점
```
원문 → [색인 표현] → (매칭) ← [질의 표현] ← 사용자 질문
              ↓                         
        후보 풀(FTS/벡터 각 500) → RRF → 상위 10 → 답/근거
```
정답 문서가 사라질 수 있는 곳은 다섯이다.

| 손실 | 설명 | 지금까지 증거 |
|---|---|---|
| L0 | 문서/청크 자체가 없다 (수집·청킹 누락) | 개발 DB 56% (F6). 운영은 해당 없음 |
| L1 | 색인 표현에 질문의 단어/의미가 없다 (어휘 간극) | 문서 확장으로 공략했으나 무변화(F3~F7) |
| L2 | 질의 표현이 문서 어휘와 다르다 | **미공략**. 동의어 사전은 정적·소규모(F2) |
| L3 | 후보 풀에는 들어오나 상위 10에 못 든다 (순위) | **미측정**. 정답이 풀 안 몇 위인지 분해 도구가 없다 |
| L4 | 상위에 있으나 답 합성이 근거를 놓치거나 틀린다 | 생성 품질 미측정(F16) |

F7은 정답이 **풀(500) 밖**이거나 풀 안에서도 낮다는 것까지는 보였지만, 풀 밖/안의 비율을 평가셋 전체에 대해 정식으로 낸 적이 없다. 이것이 가장 값싼 정보다(LLM 호출 불필요).

### 2.3 LLM(Fabrix)이 가진 것과 못 가진 것
| 강점 | 약점·제약 |
|---|---|
| 한국어/영어 혼용 의미 이해, 구어→전문어 변환 | 호출당 수 초~수십 초 (F15) → 요청 경로에 상시 넣기 어렵다 |
| 비정형 텍스트에서 구조 추출, 요약, 분류 | 비결정적. 환각 가능. 프롬프트 주입 위험(문서 내용은 데이터로 취급해야 함) |
| 사람이 하면 며칠 걸리는 판정 작업의 초안 | 콘텐츠 필터가 확률적으로 차단(FR-201), 429, 쿼터 미확인 |
| 사내 엔드포인트라 운영 코퍼스를 보낼 수 있음 (개발 OpenRouter는 운영 코퍼스 금지) | 운영 실행은 사용자가 한다. 개발에서는 크레딧이 없어 재현 불가 |

→ **비대칭의 결론**: 비용이 큰 의미 계산은 **오프라인 배치**로 한 번 하고 결과를 **검증 가능한 구조**로 굳힌다. 이미 프로젝트가 따르는 원칙(LLM 산출물은 보조 신호/후보, 근거가 아님, 사람 승인 또는 코드 검증 필수)과 일치한다.

### 2.4 "검증 가능성"이 개선 가능성의 상한
LLM 산출물을 반영하려면 맞는지 알아야 한다. 검증 수단에 따라 쓸 수 있는 범위가 갈린다.

| 검증 수단 | 예 | 반영 가능한 산출물 |
|---|---|---|
| 코드로 기계 검증 | 원문 span 존재 확인, DF 범위, 해시 일치 | 근거 연결 추출(IssueFrame), 키워드 grounded 판정 |
| 게이트(지표) | 평가셋 recall/MRR | 검색 신호 변경 — **단, 평가셋 감도가 충분해야 한다** |
| 사람 승인 | 동의어 승인, 버킷 등록, 평가 O/△/X | 새 지식·사전·평가 정답 |

실패한 5건은 두 번째 수단(게이트)에 기댔는데, 평가셋 감도가 낮아서 "무효과"와 "측정 불가"를 구분하지 못한다. **이것이 병목의 병목이다.**

### 2.5 왜 5건이 모두 무변화였나 — 가능한 설명 (우선순위순)
1. **병목이 L1이 아니다.** 정답이 후보 풀 밖이거나 질의 쪽 표현(L2)이 문제라면 문서측 신호는 닿지 못한다. (F7: 위젯 API는 확장이 켜져야 겨우 447위)
2. **어휘 간극이 합성 평가셋에서 극단적이다.** "바닥·넘어진" vs "전도"는 요약 한 문단으로 연결되지 않는다. 의미 연결은 질의→문서가 아니라 질의↔가상 질의로 풀어야 할 수 있다 (§4 H2).
3. **신호 결합이 약하다.** RRF에 세 번째 리스트를 가중해 얹는 방식은 이미 잘 맞는 문서(v2_real)의 순위를 흔들 뿐 새 정답을 끌어올리는 힘이 약하다 (MRR 하락 패턴이 일관됨).
4. **측정 감도 부족**: n=8~19, 한 건 변화 = 0.05~0.125. 작은 실제 개선은 구간에 묻힌다.
5. **개발≠운영 코퍼스(F6)**: 일부 실험은 깨진 코퍼스 위에서 이뤄졌다.

설명 1과 4는 **돈 안 드는 분해 측정**으로 가려진다 → P0.

## 3. 전체 후보 지도 (레이어별)

각 후보는 `가치 메커니즘 / 이미 한 것 / 검증 수단 / 위험 / 비용 / 권고` 순서. 비용의 Fabrix 호출 수는 처리량 약 33건/분(F15)으로 환산한다.

### A. 코퍼스 표현 (L1) — 이미 시도, 추가 투자 보류
- **문서 요약·키워드 확장**: 실패(F3~F7). 운영에서 `doc_expansion` 테이블만 남아 있고 `SEARCH_DOC_EXPANSION=off`.
- **doc2query(문서당 자연어 질문 3~5개 생성 → 질문 임베딩)**: 요약/키워드와 다르다. 질의와 같은 형식이라 e5 임베딩이 질의↔질문 유사도로 매칭하기 쉽다. **미시도.** 단, 벡터 경로 실패(F5)와 같은 병목(풀 밖)이면 같이 실패한다 → H1 상한 실험 결과가 나온 뒤에 결정.
- 비용: 대상 20천 건 × 1호출 ≈ 10시간. 임베딩 별도(개발 약 2시간/15천건).

### B. 질의 표현 (L2) — **가장 유력하나 미공략**
- **질의 재작성 / 다중 표현 생성**: 어휘 간극은 "질의 단어 ≠ 문서 단어"의 문제이므로 질의를 코퍼스 어휘로 번역하는 쪽이 문서 20만 건을 확장하는 것보다 **호출 수가 적고(질의당 1회) 방향이 직접적**이다.
- **HyDE**(가상 답변 문서를 생성해 그 임베딩으로 검색)도 같은 계열.
- 제약: 호출당 지연(F15). → **상시 호출 금지.** 1차 결과가 약할 때(FTS 0건, 상위 점수 낮음)만 폴백으로 호출하고, 결과를 질의 문자열 키로 캐시한다. 인기 질의는 오프라인으로 미리 계산해 사전화할 수 있다 (동의어 마이닝의 확장판).
- 검증: **오프라인 상한 실험**(§5 P1-a)으로 요청 경로 구현 전에 효과 유무를 먼저 본다.

### C. 순위 (L3)
- **LLM 재순위(top-20~30)**: 정답이 후보 풀 안 중위권일 때만 의미가 있다. 지연이 크다(호출당 수 초 이상). 상한 실험으로 "재순위가 이론적으로 얼마나 올릴 수 있나"를 먼저 본다(§5 P1-b). 결과가 작으면 접는다.
- 요청 경로 상시 사용은 권하지 않음(지연 게이트가 아직 없다: 백로그 #1).

### D. 답변 합성 (L4)
- 모델 후보 비교(F16): 같은 질문 20~30개로 `generation_status`, `[C#]` 인용 정합성, 지연을 비교. 쿼터 문의가 선행. 지연 대부분은 생성이 아니라 검색(약 9.5초 중 생성 4~5초)이므로 큰 이득을 기대하지 않는다.

### E. 평가·측정 (모든 개선의 상한) — **P0**
- LLM 보조 평가셋 확장: 후보 질의 생성 → 풀링 → LLM 사전 판정 → 사람 O/△/X (`evalv2` 도구가 이미 있다). Fabrix를 쓰면 운영 코퍼스 기반 평가셋도 가능하다(개발 OpenRouter는 운영 코퍼스 금지라 지금까지 불가했음).
- 실사용 질의 로그(`mcp_access_log`)에서 "결과 약함/재질의" 패턴 군집화로 평가셋 가중치 보정.
- 목표: 군당 n ≥ 30, pointer·vocab은 별도 동결(frozen) 분할 확보 → 효과 크기 0.10을 구간으로 구분 가능한 수준.

### F. 지식 생산 (L0 — 코퍼스에 답이 없음)
검색 recall과 **독립된 가치 축**이며 천장이 더 높을 수 있다. 코퍼스에 없는 지식은 검색 개선으로 찾을 수 없다.
- **실패 버킷 초안 생성**: 반복 패턴 티켓 묶음 → 버킷 이름·증상·구별 신호·원인 초안. **초안만, 등록은 사람.** (정리 갭 F13: 도메인별 수십~백여 건) 메모리의 "draft-only" 방향과 일치.
- **IssueFrame LLM 슬롯 보강**: 규칙이 못 채운 원인·조치(F11: 약 92% 공란)를 **원문 span 인용으로만** 채우고, span 존재를 코드로 검증, 실패 시 폐기. `source=llm` 표시, 근거 등급 불변. 효과는 `kb_similar_incident` 입력 품질이며 검색 점수와 무관.
- **지식 위생**: 중복·모순 문서 탐지, 오래된(stale) 문서 표시.

### G. 운영 신호 활용
- **콘텐츠 갭 리포트**: 결과 약한 질의를 LLM이 주제별로 묶고 이름 붙임 → 문서화 요청 목록. 사람이 처리.

## 4. 가설 정리 (검증할 순서)

| ID | 가설 | 틀리면 알게 되는 것 |
|---|---|---|
| H0 | 실패 케이스의 정답은 후보 풀(FTS/벡터 각 500) 밖에 있는 경우가 많다 | 풀 안이면 병목은 순위(L3) → 재순위, 풀 밖이면 L1/L2 |
| H1 | 질의를 코퍼스 어휘로 번역하면(오프라인, 상한) vocab/pointer recall이 오른다 | 안 오르면 어휘가 아니라 코퍼스/청킹/L0 문제 |
| H2 | 질의형 문장(doc2query)이 요약/키워드보다 벡터 매칭에 유리하다 | H1이 참일 때만 의미 있음 |
| H3 | 정답이 풀 안 중위권이면 LLM 재순위 상한이 유의미하다 | H0 결과에 따라 |
| H4 | 평가셋을 키우면 지금의 "무변화" 중 일부가 실제 개선/악화로 분리된다 | 그대로면 무효과 확정 |
| H5 | 지식 생산(F)은 recall과 무관하게 `kb_similar_incident`/`kb_match_failure_bucket` 응답 품질을 올린다 | 사람 평가로 확인 |

## 5. 권장 로드맵 (착수 시)

각 단계에 **성공 기준**과 **중단 기준(kill criteria)**을 미리 적는다. 문서 확장 실험에서 사후에 해석 여지를 줄이기 위해 도입한 방식이다.

### P0. 측정 기반 (LLM 거의 불필요, 1~2일)
- **P0-a. 병목 분해 도구 정식화**: `/tmp/diag.py` 계열을 저장소로 가져와(예: `apps/api/app/evalv2/diag.py` + CLI), 케이스별로 `청크 유무 / FTS 순위 / 벡터 순위 / RRF 순위 / 최종 순위`를 낸다. 요약 표(탈락 단계 분포)가 산출물.
  - 먼저 vocab 진단과 게이트 통과 수 불일치(§1 주의)를 원인까지 풀어 둘 것 (harness가 `multi_query=True`를 쓰는 반면 진단은 단일 질의 경로였을 가능성).
- **P0-b. 개발 DB 정합**: `confluence_map` 청크 없는 문서 약 35천 건을 청킹·임베딩(임베딩은 로컬 e5, Fabrix 불필요, 약 8~9시간 추정)하거나, 운영 읽기 전용 측정으로 대체. 이후 측정의 기준선은 `v2bf-off.json`을 쓴다.
- **P0-c. 평가셋 확대 계획**: Fabrix로 후보 질의·정답 후보·사전 판정을 만들고 사람이 O/△/X. 목표 군당 n≥30, frozen 분할 포함. 사람 검수 시간(1~2시간/50건 수준)이 지배 비용.
- **성공 기준**: 탈락 단계 분포를 보고 H0를 판정할 수 있다. 평가셋으로 0.10 효과를 구간으로 구분할 수 있다.

### P1. 상한 실험 (요청 경로 구현 없이 오프라인으로 "되는 아이디어인지"만 확인, 호출 수 수십~수백 건)
- **P1-a. 질의 재작성 상한(H1)**: 평가 질의 N건을 Fabrix로 "코퍼스 검색용 표현 3개"로 변환한 뒤 `multi_query` 입력에 추가해 게이트 실행. 호출 N건(≈ 1~3분). 요청 경로 코드는 필요 없다(변환 결과 파일을 하네스가 읽도록 하면 됨).
  - 성공 기준: pointer 또는 vocab recall@10 +0.10 (또는 새로 top-10 진입) & v2_real MRR 하락 없음.
  - 중단 기준: recall 변화 0이면 질의측 어휘 번역은 접는다. 병목은 L0/L1 이외(청킹 단위, 문서 구조)로 재진단.
- **P1-b. 재순위 상한(H3)**: P0-a에서 정답이 풀 안 11~50위인 케이스만 모아 LLM 재순위 후 순위 변화 측정. 호출 케이스 수 만큼.
  - 중단 기준: 개선 케이스 비율이 낮거나 케이스당 지연 > 10초면 접는다.

### P2. 구현 (P1 결과로 한 갈래만 선택)
| P1 결과 | 구현 방향 |
|---|---|
| 질의 재작성이 유효 | 폴백 모듈(조건부 호출 + 캐시 + 지연 상한 + 실패 시 원 질의) 또는 오프라인 질의 사전화(실사용 질의 로그 기반). 지연 게이트(백로그 #1)를 먼저 만들 것 |
| 재작성 무효, 재순위 유효 | 상위 N만 대상으로 하는 조건부 재순위. 지연 예산 명시 |
| 둘 다 무효 | 검색 recall 개선은 보류하고 F(지식 생산)에 투자 |

### P3. 지식 생산 (P0/P1과 병행 가능, 독립)
- **실패 버킷 초안 생성기**: 입력=반복 패턴 티켓 묶음(`kb_citec_recurring_patterns`), 출력=초안 JSON(이름·증상·구별 신호·원인), 검증=티켓 ID·인용 구절이 실제 존재, 등록=사람. 성공 기준: 사람 채택률(초안 20건 중 수정 후 등록 가능 비율). 중단 기준: 채택률 < 30%.
- **IssueFrame LLM 슬롯**: span 존재 검증 통과율, 원문에 없는 값 0건, 표본 60건 사람 분류와 대조. 중단 기준: span 검증 통과 후에도 사람이 보기에 틀린 값이 5% 초과.
  - 반영 전 `graph_sync_state` 확인(components 변경 시 그래프 증분 동기화 대상).

## 6. 하지 말 것 (이미 죽은 길과 그 이유)

1. **문서측 렉시컬 확장의 변형(AND→OR, 가중치 조정, 키워드 추가)**: F3·F4. 매칭 방식을 바꿔도 recall이 오르지 않았고 MRR만 내려갔다.
2. **확장문 벡터 경로를 같은 방식으로 재시도**: F5. P0/P1에서 병목이 풀 밖(L1)이 아님이 확인되기 전에는 가치 없음.
3. **요청 경로 상시 LLM 호출(재작성/재순위)**: 호출당 수 초~수십 초, 쿼터 미확인, 지연 게이트 없음. 조건부 폴백으로만.
4. **평가셋에 맞춰 대상 규칙·프롬프트를 조정**: 평가셋 자기참조 편향이 이미 크다. 규칙은 데이터 속성(제목 정보량 등)으로만 정한다.
5. **LLM 산출물을 근거로 노출**: `evidence_eligible=false` 유지. 요약·키워드·재작성문은 응답 근거로 인용되면 안 된다.
6. **개발 DB 결과를 운영 효과로 단정**: 코퍼스가 다르다(F6). 효과는 운영 읽기 전용 측정으로 확정한다.
7. **개인정보**: 생성 프롬프트에서 사람 이름·이메일·전화번호 생략을 지시한다(docexp 프롬프트 참고). 운영 코퍼스를 개발 OpenRouter로 보내지 않는다.

## 8. 열린 질문 / 필요한 데이터 (착수 전 확인)

1. Fabrix 분/일 쿼터와 과금 방식 (대규모 배치 전 필수; 백로그 #3).
2. Fabrix의 임베딩 엔드포인트 존재 여부와 품질(로컬 e5와 비교). 있으면 vocab 간극에 더 유리할 수 있다.
3. 다른 Fabrix 모델(`gpt-oss-120b(Low)`, `Gemma4` 등)의 JSON 준수도·지연·인용 정합성.
4. **운영 읽기 전용 측정**: pointer-only 비율, 결과 약한 질의 비율(`mcp_access_log`), 평가셋 전체의 탈락 단계 분포(P0-a를 운영 DB에 읽기 전용으로).
5. 개발 DB 정합(P0-b)을 할지, 운영 측정만으로 갈지의 결정.
6. vocab 진단 vs 게이트 불일치의 원인(§1 주의).

## 9. 의사결정 규칙 (시작할 때 쓸 체크리스트)

1. 새 개선안은 **먼저 어느 손실 지점(L0~L4)을 겨냥하는지** 적는다. 지점을 모르면 P0-a부터.
2. **사전 성공/중단 기준**을 숫자로 적고 시작한다 (문서 확장 스펙의 +0.10 기준 방식).
3. 요청 경로에 넣기 전에 **오프라인 상한 실험**으로 아이디어를 먼저 죽이거나 살린다.
4. 산출물은 **검증 수단 하나 이상**(코드/게이트/사람)을 통과해야 반영한다.
5. 게이트에 **지연 판정**을 추가하기 전에는 요청 경로 LLM 호출을 켜지 않는다 (백로그 #1).
6. 운영 쓰기·재시작은 사용자가 실행한다. 어시스턴트는 개발 DB와 스크립트까지만.
