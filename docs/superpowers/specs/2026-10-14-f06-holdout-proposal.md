# F06(R05) 홀드아웃 질문셋 제안 — 승인 요청

**상태: 제안만, 아직 동결 안 함.** 핸드오프 §3.3이 요구하는 "독립 holdout의 질문·도메인 분포·정답 근거·판정 기준은 랭킹 수정 전에 고정하고 hash를 남겨라"를 지키기 위해, 실제 질문 목록/정답을 만들기 **전에** 방법론부터 승인받는다. 랭킹 코드는 이 제안이 승인되고 실제 홀드아웃이 동결(hash 기록)되기 전까지 건드리지 않는다.

## 1. 왜 이 기존 자료를 holdout으로 못 쓰는가

핸드오프 `comparison/protocol-search.json`의 48개 검색 요청, TGW·NetApp·CITECTS-2502·기존 8개 bucket은 핸드오프 스스로 "알려진 회귀"(known regression)로 규정한다 — 이미 결과를 아는 재현용 회귀 셋이지, 독립 평가용이 아니다. 홀드아웃은 이것과 **겹치지 않는 새 질문**이어야 한다(§3.3: "평가 질문·anchor·중간 경로·support·답변 본문 모두 누출 검사 대상").

## 2. 표본 규모 + 도메인 분포 (제안)

CI-TEC 반복장애 대시보드가 쓰는 11개 도메인(`kb_citec_domain_catalog`)과, 최근 2년(`since_days=730`) 실제 분포(`kb_citec_recurring_patterns(group_by="domain")`, 삼성전자/SDS 등 실제 고객사 사건 기준)를 방금 조회했다:

| 도메인 | 최근 2년 건수 | 비중 | 제안 표본 수 (N=30) |
|---|---:|---:|---:|
| Network | 394 | 37.8% | 11 |
| 성능 | 139 | 13.3% | 4 |
| Middleware | 114 | 10.9% | 3 |
| Database | 84 | 8.1% | 2 |
| VMware | 76 | 7.3% | 2 |
| Storage | 67 | 6.4% | 2 |
| OpenStack | 55 | 5.3% | 2 |
| Kubernetes | 44 | 4.2% | 1 |
| Windows | 34 | 3.3% | 1 |
| Linux | 23 | 2.2% | 1 |
| Ceph | 12 | 1.2% | 1 |
| **합계** | **1042** | 100% | **30** |

- 비례 배분(건수 비례) + **도메인당 최소 1건**(카탈로그가 11개 도메인을 동등하게 정의하므로, 물량이 적은 Ceph/Linux 같은 도메인이 0건으로 완전히 빠지면 "관련성 비열화" 판정 자체가 그 도메인에서 아예 안 됨).
- N=30은 제안값이다 — 더 크게/작게 할지는 사용자 결정 사항. §3.3이 "작은 표본에서 통계적 일반화를 주장하지 말라"고 명시하므로, N=30은 "비열화 여부"와 "구체 질문 Top-10 포함" 판정에는 쓰되, 도메인별 정밀한 비율 비교의 통계적 근거로는 쓰지 않는다.

## 3. 질문 선정 방법 (제안)

1. 각 도메인에서 위 표의 표본 수만큼, `kb_citec_recurring_patterns`/`kb_list_tickets`로 조회되는 **실제 SWIM(incident_reports) 사건**을 무작위 추출한다(알려진 회귀 48건·8-bucket·TGW·NetApp·CITECTS-2502와 겹치지 않는 것만).
2. 평가 제외 root(`2550166358`)의 후손 문서, 그리고 핸드오프가 명시한 알려진 평가 문서 7건(`2550166369` 등)과 **관련된 질문은 선정하지 않는다** — 질문이 그 서브트리로 귀결되면 "원문 발견" 측정 자체가 오염된다(§3.3).
3. **구체 MCC/SnapMirror 유형 질문**(§2.6 검증 목표가 명시적으로 요구) — Storage 도메인 2건 중 최소 1건은 "known NetApp 회귀"와 다른 실제 사건에서 가져온, MetroCluster/SnapMirror류의 **구체적** 질문으로 채운다(broad "NetApp"가 아니라 특정 구성/장애 상황을 묻는 질문).
4. 사건 하나당 질문 1개를 사람이 쓴 자연어 증상/문의 형태로 재구성한다(실제 SWIM 제목을 그대로 복사하지 않음 — 제목 자체가 답을 노출하는 경우가 있어, 실제 유사사고 조회 시의 "질문"처럼 다시 쓴다).

## 4. 정답 근거(ground truth) 판정 (제안)

- **정답은 반드시 원문으로 판정한다**(§3.3: "평가 보고서나 그래프 출력에서 정답을 만들지 말라") — 즉 "현재 랭킹이 1위로 주는 문서"를 정답으로 삼지 않는다.
- 각 질문마다: 해당 SWIM 사건의 실제 원인 분석/조치 섹션이 참조하거나 연결된 KB 문서(문제해결 매뉴얼, 유사사고, 운영 매뉴얼 등)를 **사람이 직접 확인**해 정답 document_id 목록으로 기록한다. 이 확인은 도메인 지식이 필요한 작업이라 제가 혼자 "그럴듯한" 문서를 정답으로 지어내지 않는다 — 사용자(또는 지정하는 검토자)의 확인을 요청한다.
- 정답 문서의 `content_hash`/버전도 함께 기록한다(나중에 문서가 바뀌어도 "그 당시 봤던 원문"을 재현 가능하게).

## 5. 판정 기준 / 지표 (제안, §3.3 그대로 적용)

| 축 | 측정 |
|---|---|
| 원문 발견 | Recall@10, reciprocal rank, 원문 도달까지 실제 tool 호출 수 |
| 답변 정확성 | 원문 일치·인용 가능성, 측정과 추정 구분 |
| 비용 | 후보 수, DB roundtrip, p50/p95, 동시 요청 비용 |

- **합격 목표**: (a) 기존 구현 대비 관련성 비열화 없음, (b) 구체 MCC/SnapMirror류 질문에서 정답 원문이 Top-10에 포함. 광범위 "NetApp" 질문을 1위로 강제하는 것은 목표가 아니다(§2.6에 명시된 그대로).
- **비용 목표는 지금 정하지 않는다** — §3.3: "비용 목표가 없으면 baseline과 사용자 호출 budget을 보고 목표·이유를 고정한 뒤 수정하라." 이 제안이 승인되면, 먼저 **현재 구현**으로 이 30문항을 돌려 baseline 비용(툴 호출 수, p50/p95, DB roundtrip)을 측정하고, 그 실측값을 근거로 비용 목표를 정한 뒤에만 랭킹 수정에 들어간다.

## 6. 동결(freeze) 절차

승인되면:
1. 질문 30개 + 도메인 태그 + 정답 document_id(+hash)를 `evaluation/holdout-2026-10-14.json`에 기록.
2. 그 파일의 sha256을 `evaluation/holdout-2026-10-14.sha256`에 남기고 git commit.
3. 이후 이 파일은 **읽기 전용** — 실패 후 기준을 완화하려고 이 파일을 고치지 않는다(§3.3). 표본을 바꿔야 한다면 새 파일+새 hash로, 왜 바꿨는지 기록하고 사용자 승인을 다시 받는다.

## 7. 사용자 확인이 필요한 지점

- [ ] 표본 수 N=30과 위 도메인 배분에 동의하는지 (아니면 다른 N/배분).
- [ ] 질문 선정·재구성을 제가 초안으로 만들어 제시하고, **정답 문서 확인만 사용자(or 지정 검토자)가 하는** 방식으로 진행해도 되는지 — 아니면 질문 자체도 사용자가 고르고 싶은지.
- [ ] baseline 비용 측정을 먼저 하고 비용 목표를 그 뒤에 정하는 순서에 동의하는지.
